## 4. 必须保持的业务边界

### 4.1 定期报告校验招募说明书

- 招募说明书是待核对对象，定期报告是参考来源。
- 以招募说明书实际披露的范围为准；报告多出的股票、项目或披露不单独报差异。
- 继续支持资产组合、行业分类股票组合、股票投资明细三个既有模块。
- 按业务身份匹配，不按序号、排名或物理行号匹配；重复身份无法区分时必须说明原因。
- 境内、港股通、其他境外范围不得混配；范围分类以原文证据为依据。
- 明确未持有是有效披露。双方期间及范围对应、均明确未持有，可以一致；空数组本身不能证明未持有。
- 保留合计项、父子项目、单位和比例分母；跨页不得改变归属。
- 披露日期与数据所属报告期分别处理；沿用已确认的适用性要求，不因为迁移一律放宽或收紧。

### 4.2 定期报告校验产品资料概要，招募说明书按需补充

- 产品资料概要是待核对对象，定期报告是主参考，招募说明书只承担允许的补充角色。
- 概要、报告、可选招书可以同时作为任务输入，但每项必须明确实际采用哪个参考来源及原因，不做任意三份文件互相比对。
- 保留既有 16 项：基金简称、基金代码、基金管理人、基金托管人、合同生效日、基金经理、开始任职日期、场内简称及扩位证券简称、投资目标、主要投资策略、业绩比较基准、风险收益特征、管理费率、托管费率、审计费用、信息披露费。
- 规则按产品概况、投资与风险、费用等业务分类组织，不能按 Excel 行号分组。
- 先按语义相关章节获取完整内容；候选没命中不等于文档未披露。明确区分未检索到、证据未核实、主报告未披露和主报告不适用。
- 主报告检索失败或模型失败不能直接作为回退招书的理由。
- 管理费和托管费比较年费率，不能用实际费用金额替代；审计费和信披费须区分预估、实际、期间和费用承担范围。
- 文件发布日期不同不单独构成数据不一致；需要结合指标性质、数据期间及适用时点判断。
- 双方均无披露且不在应核对范围时，不制造空指标差异；仅目标披露而参考缺失时按真实原因说明。

### 4.3 证据与结果

- 数据结论、原文核实状态和坐标定位状态分别保留，定位失败不能清空已经识别的值。
- 不能在没有足够原文依据时强行判一致；继续保留真实的待复核和不适用状态。
- 金额、日期、代码等可确定比较继续采用通用程序能力；模型承担语义对应及业务条件识别。
- 模型提供引用或来源候选，坐标仍由真实 PDF 解析结果生成，不能采信模型编造的坐标。

## 5. 中文规则文档设计

### 5.1 文件与分类

保留当前模块、指标的稳定身份，优先沿用现有文件定位，避免历史任务及调用关系同时迁移。正文使用中文主标题及以下区域：

| 中文标题 | 内容 | 示例 |
| --- | --- | --- |
| 核对内容 | 对象、指标、核对范围 | 只比较管理费年费率 |
| 查找位置 | 不同文档的优先章节及相近表达 | 定期报告的管理人报酬、关联方报酬 |
| 来源选择 | 主来源、补充条件 | 主报告确认未披露后查招募说明书 |
| 判断标准 | 对应关系、可比条件、判定方式 | 同基金同份额、同适用条件下比较年费率 |
| 特殊情况 | 业务例外和不确定处理 | 已披露费率调整但生效时间不明确时说明原因 |

区域由页面提供。只强制标题名称和正文结构以便呈现，不把某个固定句式、标点或关键词命中当作业务执行条件。主标题和核对内容必填，其他区域允许继承公共规则；业务条件确有缺口时给出具体中文提示。

公共规则保存身份、来源、期间和证据等共享业务要求；指标规则不重复整份公共要求。适用任务、公共规则版本、文件身份由系统维护。

管理人员正文中不再出现：TOML/JSON 参数区、英文策略枚举、固定业务行键全集、列键映射、Excel 行号、坐标协议、跨页列边界容差。

Excel 坐标仅作为原需求溯源资料保留，不参与路由、分组或判断。算法阈值及输出协议留在开发侧系统层，不放入业务正文。

### 5.2 样稿：管理费率

```markdown
# 管理费率

## 核对内容
核对产品资料概要披露的管理费年费率，不比较当期实际发生的管理费金额。

## 查找位置
产品资料概要优先查找“基金运作相关费用”。
定期报告优先查找“基金管理费”“管理人报酬”或“关联方报酬”等相关章节。
招募说明书优先查找“基金的费用与税收”及管理费计提相关段落。

## 来源选择
优先采用适用的定期报告。主报告确认未披露年费率时，允许使用招募说明书补充，
并确认该费率适用于概要编制时点。

## 判断标准
确认基金、份额类别及费率适用条件对应后，比较年费率。

## 特殊情况
发布日期不同不单独构成费率差异。发现费率调整时核对生效日期；
适用时间无法确认时，说明缺少什么依据。
```

### 5.3 样稿：资产组合情况

```markdown
# 基金资产组合情况

## 核对内容
以招募说明书披露的资产组合项目为范围，核对金额、占基金总资产比例和合计。
定期报告额外披露、招募说明书未披露的项目不单独提示差异。

## 查找位置
查找两份文件投资组合报告中的资产组合情况，包含续页、表注及子项目。

## 来源选择
以适用的定期报告作为参考，确认双方数据所属报告期和基金身份对应。

## 判断标准
按项目含义和上下级关系对应，不按序号、行顺序或所在页对应。
金额单位、比例分母和数据期间对应后，再核对披露值。

## 特殊情况
合计项单独核对，不用自行计算的结果替代原文披露。
横线、数值零、空白和未识别须区分。原文明确未持有时保留该披露及其适用范围。
```

## 6. 后台衔接方案及约束

### 6.1 保留统一协议，解除业务规则对代码格式的依赖

- 系统维护稳定规则 ID、任务类型、分类、展示顺序和文件关系。改标题不改变历史身份，不使用英文指标 ID 分支决定业务口径。
- 保留现有结果与证据接口；需要内部适配时集中转换，避免前后端、历史任务和模型输出同时破坏兼容。
- 不建立第二份需要人维护的策略配置。技术登记信息中不得复制一套来源顺序、期间政策、行名全集等业务要求。
- 全面列出旧字段的消费者并逐项替换；不能只更改加载器，遗漏源表补全、缓存、预检或比较函数。

### 6.2 规则解释只在版本变化时进行

采用“中文规则 → 系统生成并校验通用声明式计划 → 通用执行器”的衔接方式。计划由系统生成，管理人员无需编辑；不能只是把旧 TOML/Markdown 参数模板重新生成一遍，再由旧代码路径继续决定业务行为。

执行信息至少覆盖：核对对象与范围、各角色章节线索、来源条件、比较对象及可比条件、完整性要求、需要保留的特殊披露。范围、期间、份额和费用性质等关键条件必须有对应的规则原文依据。

- 模型仅将业务文字解释为受约束的数据结构，不能生成并执行 Python、SQL、文件操作或任意表达式。
- 程序校验结构、支持的能力及规则冲突，不通过就返回具体中文问题；不臆造业务缺省值补齐。
- 章节线索是优先搜索范围，不是必须逐字匹配的词表。未命中时使用有记录、有范围的扩展检索，不默认发送全文。
- 完整逻辑表、续页及子章节由文档层提供，不因缩小检索范围截断；不把跨页算法重新交给逐指标业务规则配置。
- 金额归一化、日期解析、原文核验和定位仍调用共享能力，不能借“自然语言”取消这些校验。
- 模型解释能力不足时明确阻塞的语义，不回到为某个指标 ID 增加 if/else 的做法。
- 业务代码审计必须清除按 `item_id`、`module_id`、规则文件名、标题或标签切换业务含义的分支。稳定注册表只可定位规则文件和保持历史身份，不能决定比较行为。
- 逐项审计 `app/domain.py`、`app/extraction.py`、`app/comparison.py`、`app/summary_rules.py`、`app/summary_check.py` 的规则消费者。投资组合比较器当前资产、行业、股票各自的 ID 条件，须改由执行计划声明身份字段、范围字段、比较集合方向、数值字段和辅助字段，再交给共享匹配器执行；迁移中不得丢失现有范围、证据及报告多披露不报差异等边界。
- 概要执行不得以固定指标 ID 或旧元数据表作为业务真值。Python 可保留受限通用操作与安全校验，但策略参数必须由中文正文编译生成。

### 6.3 保存、激活、缓存和失败行为

1. 用户修改分区文本，点击一次保存。
2. 校验正文，并结合所属公共规则生成执行信息；显示保存进度。
3. 校验通过后，原文版本和执行信息版本一起激活。成功提示明确新任务生效。
4. 失败时保留用户输入，指出原因；旧生效版本保持原状，并明确本次修改尚未生效，不能报“已保存生效”。

不要为所有修改添加额外人工审批步骤。必要的歧义只在具体区域提示，不让用户填写内部枚举。

- 缓存至少绑定正文哈希、公共规则哈希、解释协议版本、解释提示词版本和解释模型版本；相同版本不重复解释。
- 一次成功激活固定其解释结果，任务复用该结果，不能每次随机重生成覆盖。
- 公共规则更新要使依赖它的执行信息失效并完成整组校验；存在失败时不留下半组新规则、半组旧规则的隐式混用。
- 每个任务开始时固定整套适用规则快照，运行中编辑不能让同一任务前后使用不同版本。
- 保存保留现有哈希冲突检查与原子文件写入；新原文、新执行信息和激活指针必须一致，异常可回滚。
- 模型返回无效结构或服务故障时采用有限恢复，记录原因；不无限重试、不静默采用旧业务参数覆盖新正文。

## 9. 测试要求

### 9.1 测试原则及独立预期

- 单元及接口测试覆盖实际变化，不用“实现输出等于实现输出”的自证测试。
- 不因新旧结果相同就认定业务正确。独立预期来自原始 PDF，记录文件哈希、物理页码、原文、范围及预期来源。
- 现有 `evaluation/cases/manifest.json` 有 5 个产品、15 个案例，但部分预期标记 `PENDING_INDEPENDENT_PDF_REVIEW`，部分为 `READY_WITH_UNCONFIRMED_ITEMS`。这些不能当作已确认真值，须补做 PDF 核对并保留未确认状态。
- 无法从给定文件确认的业务结果，预期应为准确说明原因的无法确认或不适用，不能为了通过测试强行设为一致。
- 测试规则编辑必须使用临时规则目录或隔离测试实例，不篡改实际业务规则、已完成历史任务和输入 PDF。
