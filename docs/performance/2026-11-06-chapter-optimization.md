# 2026-11-06 章节识别准确性与性能优化

## 实测范围

使用项目现有上证 50 招募说明书（122 页）、2025 年第 4 季度报告（14 页）和 2026 年第 2 季度报告（14 页）。模型沿用本地 Codex API 的 gpt-6-luna，全局请求并发为 3。耗时包含本地后台执行及客户端每 2 秒轮询，属于开发机样本数据，不代表所有产品与所有 PDF 的准确率或稳定吞吐量。

## 最终结果

| 场景 | 优化前 | 优化后 | 结果 |
|---|---:|---:|---|
| 相同内容，强制调用模型 | 139 秒 | 34.170 秒 | MATCH，0 差异 |
| 相同文件，已验证章节缓存命中 | 无缓存 | 4.031 秒 | MATCH，0 差异，6 个章节命中 |
| 更换为 2026 年第 2 季度报告 | 147 秒，双方均重新提取 | 20.113 秒，复用招书的 3 个章节 | 60 项差异，明细与原基线一致 |

首次一致任务耗时较原样本减少约 75%。新模型请求累计输入 36,114 字符（原 62,490）；返回累计 13,120 字符（原 45,123）。这里统计的是字符数，不是 token。

每份文件分别覆盖 12 行资产、20 行行业（含合计）、10 行持仓，共 94 个数值字段。两组文件的数值类型、规范值及原有明确单位与基线逐字段核对通过，全部字段有 LOCATED 证据；最终差异集合分别为 0 和 60，与基线的行业/证券、字段及两边数值一致。续页金额和比例单位均由已确认前表头继承。

不同基金的拒绝样本返回 FUND_MISMATCH，未触发章节模型请求。33 项受影响检查通过，覆盖跨页完整性、来源 ID 错误/重复/漏行、同名行定位、未知市场的唯一证券配对、市场冲突拒绝、缓存失效、局部重试、并发上限及历史 PDF 预览。

## 实施内容

1. 章节来源页补充唯一表格行和正文锚点，招书行业章节覆盖 55、56 页。
2. 为完整映射的源表行分配来源 ID。模型确认身份、父子关系和范围，程序从源表取回数值、单位、页码与坐标。Markdown 把续页表格行转成普通下划线正文时，也按完整原文行与源表关联。
3. 核验每个来源 ID 恰好覆盖一次，未知、重复和遗漏都不能直接产生“一致”。源地址还需通过真实表格、字段列、行名及值复验。
4. 按章节并发，默认全局最多 3 个模型请求；错误章节独立重试一次，成功章节独立持久缓存。接口总超时包含 SDK 内部重试，排队耗时单独记录。
5. 缓存键包含 PDF 哈希、角色、提示词、模块规则、公共规则、模型、接口地址与相关代码版本。命中后仍重新绑定并验证 PDF；force_refresh=true 可强制重新识别。
6. 未知市场只在证券代码各自唯一、投资范围无冲突时配对；明确市场或投资范围冲突继续待复核。提取不完整时禁止据此报单侧出现；无法确认行身份不能静默跳过后判一致。
7. AnyDoc 和产品日期预检查使用独立进程，避免在同一进程的多线程中并发调用 PyMuPDF。模型客户端复用连接并记录排队、请求耗时、token 用量及结束原因。

## 使用与边界

上传接口 `POST /api/jobs` 可附加 multipart 参数 `force_refresh=true`，用于跳过读取缓存的模型稳定性测试。设置 `PROSPECTUS_CACHE_ENABLED=0` 可关闭缓存。

本次是章节提取缓存；PDF 解析仍会执行。成功章节可供重新提交复用，尚未实现原任务 ID 的自动断点恢复。扫描件 OCR、其他产品的大样本准确率和多用户负载不在本轮验证范围内。无法完整建立表格来源目录的章节继续采用原文引用提取并保留结构疑点，未通过验证的内容不编造为一致。
